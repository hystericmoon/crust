Making the Crust app itself friendly

You said the app isn't very nice or friendly to use, and asked how Squarespace, Wix and Webflow do theirs. The short answer: Crust's words and choices are already kind, but the editor feels like a developer tool. You see a small page, a long list of block names and a search-engine form. The three big builders all make the page the main thing on screen and keep tools hidden until you need them.

Worth copying

  • "+ Add section" between sections, opening a gallery with pictures (we already have the 90-layout gallery)
  • Split the work three ways: the page (on the canvas), the look (one paintbrush), site details (a settings sheet)
  • One clear status: "Saved · 3 changes not live", and a Publish button that shows the count
  • Pages grouped "In the menu" and "Not in the menu"
  • A short "next steps" list for a new site, with a skip
  • Cmd+K to find any page or setting

Worth avoiding

  • Webflow's CSS ideas (classes, flex) and dense dark chrome: too steep for our users
  • Wix's crowded top bar (16 items, with upsells)
  • Squarespace's "save = live" (Crust users rely on a separate Publish)
  • Free positioning anywhere on the page: it breaks on phones
  • Several editors or modes for the same page

4 · Accessibility

To fix whichever direction you pick

  • The editor has no main area marked and no top heading, so screen-reader users can't jump to the work area or tell where they are. WCAG 1.3.1 · 2.4.1 · 2.4.6
  • 30 pieces of the block list and side panels sit outside any labelled area: they need to be marked as named regions (Add, Inspector). WCAG 1.3.1
  • Dragging blocks is announced with an outdated attribute (aria-grabbed). Use spoken status messages instead. The keyboard way to move items already exists and stays. WCAG 4.1.2
  • The section toolbar's colour dots are about 16px and unnamed. Make them at least 24px, and give each a name ("Background: Sand"). WCAG 2.5.8 · 1.1.1
  • When you tab through the page, the floating toolbar can cover the item that has focus. WCAG 2.4.11
  • The "Site header · edit in Site settings" labels on the canvas are tiny, faint text. WCAG 1.4.3
  • The template banner shows success or failure only with a coloured side bar. Its heading should say the result in words. WCAG 1.4.1
  • Still to check: the page inside the editor wasn't scanned (the automatic tool can't reach into it yet), and 13 block-list labels need a contrast check by hand. WCAG 1.4.3
5 · Proposed work for A

In the order I'd build it

Each is one feature, one PR and one review. They're proposals only (in DECISIONS.md → Proposals): nothing is built until you say which to add.

  1. One app frame and top barSite menu (switch sites), page switcher, status ("Saved · 3 not live"), Preview, Publish as the one main button with the count. Left icon bar. Same words everywhere ("Publish", "Back to …").Medium · fixes 1, 8, 11
  2. Page firstOpen a site straight onto its home page at fit width. The block list moves into the Add panel. The right panel appears only on selection, with "Next steps" when nothing is selected.Medium · fixes 2, 3, 4
  3. Add section, by picture"+ Add section" between sections opens the layout gallery (Intro, Gallery, Text…, Blank, My layouts). Single blocks sit under it as "Add an element".Small–medium · reuses F080
  4. One-row section toolbarSection · Style · Layout · Move · More. Site-wide actions ("change everywhere", "make linked") go under More, with a step that says how many sections and pages it affects.Small · fixes 5, 6
  5. Type on the pageClick a heading or text and edit it in place, with the rich-text bar floating above it. Quick edit stays as a list view for long pages.Large · the biggest single step toward "friendly"
  6. Pages panel"In the menu" and "Not in the menu", drag or arrow keys to reorder, a status dot per page, page settings (title, search and sharing) behind each page's ⋯.Medium · replaces the site home table
  7. Styles panel and Site settings sheetPaintbrush panel: Styles cards first, then Fine-tune (colours, type, buttons, spacing, motion), and Header & footer. Site details (address, search defaults, where to publish) in a separate sheet.Medium · fixes 10
  8. The app's own look and wordsOne accent colour across the app, a type pairing for the chrome, and a wording pass (including the ~70 "GitHub" strings from F055).Small–medium · fixes 7
6 · Your call

Three questions

Which direction?My pick is A. B if you want a "manage" home for later features (store, analytics); C if you'd rather keep changes small for now.
Drop "Save draft"?A works best when changes save on their own and the status says so. The desktop app can save to your computer quietly. In the browser, each save is a GitHub save, so I'd group them every few seconds. Keep the button, or let it go?
Which features to add?Pick from the 8 above. I'd start with 1–3: they change how the app feels most, for the least work.
How to answerReply in chat, for example "A, autosave yes, add 1–4". I'll add your picks as features and draw a design snapshot before building each one.
